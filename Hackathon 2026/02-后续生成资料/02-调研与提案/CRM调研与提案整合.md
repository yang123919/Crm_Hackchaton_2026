# CRM 调研与提案整合

> 本文把 Claude 长文、CRM 演示视频审阅 PDF、赛前题目背景和团队已确认的约束合并为一个版本。重复的 Claude Code 选型、Android/Firebase 建议和多套重复 Q&A 已删减；结合组长新发的 QuickLead 手机线框图和团队正在 Vibe Coding 的状态整理；技术栈以组长当前代码库为准。甲方没有确认的系统能力标为“待确认”，不作为既定事实。

## 结论先看

- **项目方向：** 做手机优先的响应式 CRM 网页，让外勤销售现场快速记录 Contact 跟进，并设置下一步与提醒。
- **技术边界：** 线框图定义手机端体验；沿用组长当前项目，Android 或响应式网页都可。MySQL 必须通过后端/API 访问，不能由客户端直连。
- **AI 边界：** 赛题写明 AI-powered solution，完全不用 AI 有偏离题目的风险。建议只做一个轻量功能：把销售输入的短跟进笔记整理成结构化摘要和下一步建议，由销售确认后才保存。不要先做语音识别、证件 OCR、自动评分或大型聊天机器人。
- **先问清楚：** 甲方说的“转换成一种格式”究竟是什么输入、什么目标格式。确认前，不要声称 AI 已解决这个流程。

## 2. 甲方已表达的痛点

根据你们的访谈整理，外勤销售目前主要用 Laptop 录入 CRM；手机页面不便、表单字段多，销售无法在见客现场快速记下信息，回到桌边再录容易延迟或忘记。流程包含 Contact 和 Opportunity；甲方表示比赛原型可以用 mock data，现有系统数据库使用 MySQL。

你们还听到“要把资料转换成一种格式”，但目标格式、来源和转换责任人尚不清楚。这是需求澄清项，不能直接假设为 Excel/CSV，也不能直接认定一定要由 AI 转换。

CRM System Demo Video Review PDF 将视频描述为 Euro Auto 的汽车销售 CRM 演示，画面包括 Lead、Convert、Opportunity、报价/融资、文件生成、Kanban、筛选、批量导入和 Account 导航。视频/总结中出现的 SuiteCRM 判断来自外观推测；没有证据确认甲方实际部署版本或 API 配置。[SuiteCRM 官方 Demo 页面](https://suitecrm.com/demo/)说明其公开演示包含 SuiteCRM 7 ESR 和 SuiteCRM 8；这不能证明 GCR 的定制系统与公开 Demo 完全相同。

| 观察/线索 | 可改进方向 | 确认状态 |
|---|---|---|
| 桌面表单字段密集、多个 Tab、字段较多 | 手机首屏只显示快速跟进必需字段，其他字段折叠到“更多资料” | 来自现有访谈与视频画面线索；请甲方确认哪些字段必填 |
| 录入动作需要回到 Laptop | 响应式网页、客户详情中的大按钮“快速记录” | 痛点已由甲方口头表达；需确认手机浏览器/网络环境 |
| 演示视频显示有 Lead、Opportunity、阶段、报价和文档功能 | 不重做完整 CRM；聚焦移动跟进入口及与现有 Contact/Opportunity 的关系 | 画面可见，但具体当前功能以甲方系统为准 |
| 视频画面似乎把历史跟进放在 Description 等文本区域；Kanban 出现 Follow Up 阶段和红色日期 | 每次跟进单独成条，包含时间、内容、下一步、下次跟进日；显示今日/逾期提醒 | 仅为画面观察，需问甲方是否已有独立日志和通知 |
| 有客户资料/联系信息画面 | 演示只用虚构/获准的脱敏数据；避免在 slides 或录屏展示真实个人信息 | 必须遵守；若使用甲方数据先询问授权 |

### 功能优先级

**第一版必须做：** 手机快速录入、结构化跟进记录、下次跟进日期、今日/逾期清单、Contact 关联。

**时间够再做：** Opportunity 轻量关联、点按打开 WhatsApp 的预填文字（先不自动发出）。

**本次暂缓：** 证件/IC 识别、名片 OCR、AI Lead Scoring、经理仪表板、完整销售阶段自动化。这些超出短时原型范围，也需要额外隐私、接入或数据要求。Android 与网页由组长根据现有代码决定，不在本文另行选栈。

## 4. 最适合团队的网页实现方式

```text
手机浏览器/电脑浏览器
   ↓ HTTPS JSON API
后端接口（校验表单、业务规则）
   ↓ 参数化 SQL
MySQL
```

- **前端：** 团队会用的 HTML/CSS/JavaScript 或现有网页框架，采用 mobile-first 响应式布局。
- **数据库：** Contact、Activity、Opportunity 三类数据；Activity 用一条记录表示一次跟进。
- **后端：** 需要一层 PHP/Node 等 API，或使用甲方提供的现成接口。若团队没有后端经验，优先询问是否有测试 API/样例；否则准备 localStorage/mock 模式演示，不要声称它已经写入 MySQL。
- **AI：** 把原始跟进文本发给获准的模型 API，取回 `summary` 与 `next_action`；显示在可编辑表单里，由用户按“确认保存”。API Key 放后端环境变量，不放在网页 JS。
- **异常回退：** AI/API 失败时，保留原文，仍可手动保存；演示准备 mock AI 结果。
- **不依赖：** 证件 OCR、真实 CRM API、外部 WhatsApp Business API。按新线框图，语音输入是理想主路径，但必须保留手动输入以覆盖权限/语音失败。

## 5. 现在最值得问甲方的三题

若时间只够问三题，照下面顺序问，并记下原话与数字：

1. **确认“统一格式”**：「您提到客户资料需要转换成一种格式。资料原本从哪里来，最后要转换成什么格式？可以给我们看一个脱敏的输入和目标样例吗？」
2. **确认提醒与跟进**：「现在 CRM 会提醒销售今天或逾期要跟进的客户吗？销售目前怎样记录每次跟进、怎样记住下次联系时间？」
3. **确认最小字段和基准时间**：「外勤销售新增一条客户/跟进记录，哪些字段是必须的？现在用 Laptop 录一条通常要几分钟？」

如果还能多问：

- 「手机浏览器能否访问现有系统？你们有没有测试环境或 API 可以让我们接入？」
- 「比赛提供的数据是否可用于投影、录屏或 AI API？哪些字段必须脱敏？」
- 「WhatsApp 是否是销售主要联系客户的渠道？你们希望系统只是准备文字，还是要正式发送？」

## 6. 7 分钟演示建议

已知展示时间为 7 分钟、演示后没有 Q&A。目标排练到 6 分 30 秒，留出现场操作缓冲。

| 时间 | 内容 |
|---|---|
| 0:00–0:40 | 一句话痛点：外勤销售见完客户后还得等 Laptop 录入，信息会延迟或遗漏 |
| 0:40–1:20 | 甲方当前流程和已确认的数据/格式问题；不要把推测讲成事实 |
| 1:20–2:00 | 方案与页面流程：Contact → 快速记录 → 确认保存 → 下次跟进提醒 |
| 2:00–4:10 | QuickLead 手机 Demo：Today → Capture（语音/手动）→ AI 整理 → Review 确认 → Lead detail/Follow-up history → WhatsApp 草稿 → Today |
| 4:10–5:10 | MySQL/API 或 mock 架构、数据隐私、AI 失败时的手动回退 |
| 5:10–6:10 | 业务价值：用 Q&A 获得的基准分钟数和每日客户量估算节省时间；没有数据就不编数字 |
| 6:10–6:30 | 总结并回到“让销售在客户现场把跟进记下来” |

录制一份备用 Demo；一人讲解、一人操作。正式前确认视频中的姓名、电话、IC 等信息已脱敏。
